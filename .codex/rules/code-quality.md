# Code quality rules

- Prefer simple, readable and explicit code.
- Avoid over-engineering and speculative abstractions.
- Use early returns when they make control flow clearer.
- Keep functions, components and classes cohesive; split them when responsibilities become mixed.
- Use names that reveal intent and follow the language and project conventions.
- Comments should explain why, constraints or non-obvious trade-offs, not repeat what the code says.
- Remove dead code, debug logs, temporary files, unused imports and commented experiments.
- Do not suppress compiler, linter or analyzer errors without a documented and justified reason.
- Keep changes focused on the requested task.
